1. System overview

The app is a RAG-backed AI gym trainer: a vanilla JS frontend talks to a FastAPI backend. An LLM agent (Ollama local or Gemini cloud) owns the conversation and calls Python tools that search a pre-built exercise vector database. Logged-in users get adaptive difficulty and workout history in SQLite.

3. Design patterns used

Pattern Where Why
RAG (Retrieval Augmented Generation) rag_store + embeddings + tools LLM does not memorize 873 exercises; tools retrieve real data from vector DB
LLM tool / function calling providers.py Model decides when to call plan_workout or find_exercise
Agent loop (multi-round) OllamaConversation.send() Round 1: tool call → Round 2: forced text summary (budget from OLLAMA_TOOL_ROUNDS)
Strategy (provider swap) start_conversation() Same tools + prompts; swap Ollama vs Gemini via AGENT_PROVIDER
Factory app/agent/__init__.py → start_conversation Creates the right conversation object for the configured provider
Collector (shared mutable list) collector: list[dict] passed to tools Tools append exercises; provider returns deduped list to API → frontend
Session state (in-memory) main.conversations session_id → {conversation, user_id}; LLM keeps full message history
State machine progression.next_levels() beginner → beginner+intermediate → intermediate → intermediate+expert
Normalizer / alias map muscles.normalize_muscles() "abs" → abdominals, "legs" → quad+ham+calves+glutes, "back" → lats+mid+lower
Singleton / cache @lru_cache get_local_model(), _store_cache Embedding model and RAG matrix loaded once per server process
Dependency injection Depends(auth.current_user) Protected routes auto-resolve user_id from Bearer token
Offline-first build, online query build_embeddings.py vs runtime search Documents embedded offline; runtime only embeds short muscle queries
Fallback chain _collect_unique() in tools Planned levels → fallback levels → allow repeats if DB exhausted

7. Chat request flow (end-to-end)

sequenceDiagram participant UI as web/index.html participant API as POST /api/trainer/chat participant S as conversations map participant AG as Agent (Ollama/Gemini) participant T as tools.py participant DB as SQLite + rag_db UI->>API: {message, session_id?} + Bearer token API->>API: is_store_ready? is_agent_enabled? API->>API: resolve user_id from token alt new or foreign session API->>AG: start_conversation(user_id) API->>S: store session_id → {conversation, user_id} else reuse session API->>S: get existing conversation end API->>AG: conversation.send(message) AG->>AG: LLM decides: text only OR tool call opt tool call AG->>T: run_plan_workout / run_find_exercise T->>DB: RAG search + log workout T-->>AG: tool result JSON AG->>AG: second LLM round (summary) end AG-->>API: (reply text, exercises[]) API-->>UI: {type, sessionId, reply, exercises} UI->>UI: render chat bubble + exercise cards

Session rules

  • Each session_id is tied to one user_id.
  • If session_id is missing, invalid, or belongs to another user → new UUID session.
  • Conversation object holds full LLM message history (for "next exercise", "repeat", etc.).
  • Sessions live in memory only — server restart clears them; workout history stays in SQLite.

8. LLM agent + tool-calling loop (Ollama)

Gemini uses native automatic function calling in one SDK call. Ollama uses an explicit multi-round loop:

flowchart TD A[User message appended] --> B{Round < budget?} B -->|yes| C[POST Ollama /api/chat
with OLLAMA_TOOLS] C --> D{tool_calls in response?} D -->|yes| E[Execute each tool
OLLAMA_TOOL_REGISTRY] E --> F[Append tool result to messages] F --> B D -->|no| G[Return text reply + collector] B -->|final round| H[Inject: do NOT call tools] H --> C G --> I[dedupe exercises by name] I --> J[Return to main.py]

Two tools only:

ToolWhen LLM calls itPython function
plan_workoutUser names muscle(s) for a workoutrun_plan_workout()
find_exerciseUser names one specific exerciserun_find_exercise()

No tool (LLM text only): greetings, "next exercise", "repeat", "stop", general chat.

9. plan_workout tool — full RAG pipeline

flowchart TD START[run_plan_workout muscles, counts, level] --> PARSE[Parse groups + explicit counts] PARSE --> SPLIT{distribute counts} SPLIT -->|no counts| AUTO[Split DAILY_EXERCISE_TOTAL=15 across groups] SPLIT -->|partial counts| FILL[Explicit + remainder to unspecified] SPLIT -->|all explicit| USE[Use exact counts capped at MAX=30] AUTO --> LOOP[For each muscle group] FILL --> LOOP USE --> LOOP LOOP --> EMB[embed_text: muscle + exercises] EMB --> CANON[normalize_muscles → canonical key] CANON --> LEVEL{level given?} LEVEL -->|yes| FIX[Use explicit level] LEVEL -->|no + user_id| PROG[progression.next_level_plan] LEVEL -->|no + anonymous| ANY[Any level search] FIX --> UNIQ[progression.served_names 7-day window] PROG --> UNIQ ANY --> SEARCH UNIQ --> SEARCH[_collect_unique → rag_store.search_exercises] SEARCH --> PHASE1[Phase 1: fill per level plan] PHASE1 --> PHASE2[Phase 2: fallback levels if short] PHASE2 --> PHASE3[Phase 3: allow repeats if still short] PHASE3 --> LOG[storage.log_workout per group] LOG --> COLL[Append to collector with group + image URLs] COLL --> LOOP LOOP --> DONE[Return groups + total to LLM]

RAG search internals (rag_store.search_exercises)

  1. Load cached matrix: 873 × 384 embeddings + exercise JSON
  2. Cosine similarity: query vector vs all exercise vectors
  3. Optional hard filter: level=beginner|intermediate|expert
  4. Optional exclude: names already served in 7-day window
  5. Keyword boost: +score if query tokens match primary muscle or level
  6. Return top_k exercises sorted by final score

11. Adaptive difficulty state machine

Reads most recent prior day within 7 days (same-day repeats do not advance).

stateDiagram-v2 [*] --> BeginnerOnly: no history / gap > 7 days BeginnerOnly --> BeginnerMixed: last day was beginner only BeginnerMixed --> IntermediateOnly: last day was beginner + intermediate IntermediateOnly --> IntermediateExpert: last day was intermediate only IntermediateExpert --> IntermediateExpert: last day was intermediate + expert (cap)
Last session levels (prior day)Next plan
(none)100% beginner
{beginner}50% beginner + 50% intermediate
{beginner, intermediate}100% intermediate
{intermediate}50% intermediate + 50% expert
{intermediate, expert}50% intermediate + 50% expert (cap)
